Як зайти в u.Освіта і нічого не зламати

Не екскурсія по папках, а порядок входу в проєкт: що запустити, які доступи забрати, де шукати синхронізацію і що перевірити до першого коміту.

Node.js + TypeScript PostgreSQL + Prisma Redis + BullMQ React Admin SPA

1. Що саме передається

u.Освіта — монорепозиторій із трьома окремими runtime-компонентами: Express API, BullMQ worker та React Admin SPA. Проєкт обслуговує мобільний застосунок, локальну PostgreSQL, зовнішню систему університету, OTP/SMS/email і банківський процесинг.

Головне правило підтримки: API без worker виглядає працездатним, але синхронізації не виконуються. Під час діагностики завжди перевіряйте API, worker, PostgreSQL і Redis окремо.

               ├→ Express routes → validation → controller → service → Prisma → PostgreSQL

                                                      ├→ зовнішні API

У проєкті немає окремого repository layer: більшість сервісів звертається до Prisma напряму. Маршрути мобільного API змонтовані на /v1, адміністративного — на /admin/api, production SPA — на /admin.

6. Ключові бізнес-потоки

Авторизація

Телефон → OTP → User → password → access/refresh JWT. Refresh token зберігається у БД. Невдалі входи збільшують лічильник і можуть заблокувати login до recovery.

Верифікація студента

Авторизований користувач вибирає організацію → backend запитує `/studentinfo` → створює `UserStudent`, department/group → ставить фонові jobs.

Синхронізація

API додає job у Redis → worker викликає зовнішній API → нормалізує відповідь → змінює дані та `StudentSyncStatus`/`OrganizationSyncStatus`.

Платіж

Створення `StudentPayment` → payment link або token purchase → 3DS → callback/webhook → перевірка стану → `PaymentTranState`.

7. База даних і міграції

Prisma-схема містить 28 моделей. Критичні зв’язки: `User → UserStudent → Department → Organization`, а також `StudentPayment → PaymentTranState`.

Правила змін

  1. Не редагувати вже застосовані production-міграції.
  2. Створювати нову міграцію і переглядати SQL до застосування.
  3. Перевіряти міграцію на чистій БД та копії production-схеми.
  4. Планувати rollback або forward fix для незворотних змін.
  5. Після зміни схеми запускати `prisma generate`, TypeScript build і tests.
Відоме розходження: Prisma enum містив `SyncStatus.SUSPENDED`, але всі 29 міграцій не створювали це значення у PostgreSQL. У локальній тестовій БД воно було додано вручну; для репозиторію потрібна коректна міграція.

8. Redis, BullMQ і worker

Окремі черги існують для розкладу, екзаменів, оцінок, навчального плану, новин, платежів, знижок і recovery. Worker створює consumer для кожного типу з concurrency 5; janitor має concurrency 1.

Під час проблеми перевірити

  1. Чи доступний Redis.
  2. Чи запущено worker deployment.
  3. Waiting/active/failed jobs і repeatable configuration.
  4. Чи не залишився DB status `RUNNING` після падіння.
  5. Чи збігаються cron у PostgreSQL та Redis.
  6. Чи є job idempotent при повторному запуску.
Транзакція Prisma не охоплює Redis. Можливий стан «БД оновилась, job не створився» або навпаки. Це потрібно враховувати при recovery.

9. Admin SPA

React 19 SPA використовує React Router, TanStack Query, Zustand, Axios, Chart.js і Tailwind. Серверні дані мають залишатися в TanStack Query, локальний UI state — у Zustand.

Маршрути

  • Dashboard;
  • Students і Student Inspector;
  • Student Invite;
  • Jobs;
  • Organizations і Organization Detail.

Перевіряйте одночасно три префікси: React Router `basename`, Vite `base` і Express mount. Зараз `/admin`, `/admin/api` та `/api/admin` не повністю уніфіковані. У репозиторії також залишились старі EJS-сторінки.

10. Мінімальні перевірки перед зміною

# Backend build
npm run build

# Admin build
cd admin-spa && npm run build

# Runtime
curl http://127.0.0.1:3000/v1/actuator/health
redis-cli ping
psql -d mydb -c "select now();"

У `tests/integration` є тести auth, university, processing і transliteration. Штатний `npm test` зараз потребує виправлення: він викликає відсутній script `db:push`. Не вважайте зелену TypeScript-збірку доказом працездатності міграцій або інтеграцій.

Обов’язкові набори тестів, яких бракує

  • authorization для кожного admin endpoint;
  • tenant isolation;
  • чиста послідовність усіх міграцій;
  • contract tests відповідей університету;
  • idempotency і retry jobs;
  • callback/webhook security;
  • end-to-end login, student verification і sync.

Добра перша задача: виправити test script, додати migration test і закрити auth на одному наборі admin endpoints. Не починати передачу з великого рефакторингу sync engine.

13. Релізний чек-лист

  1. Зміни переглянуті іншим розробником.
  2. Backend і admin SPA збираються.
  3. Tests і migration test зелені.
  4. Нові environment variables описані без секретів.
  5. Міграція перевірена й має план відновлення.
  6. Не змінено callback URLs або queue names без узгодження.
  7. Оновлені версії package та Helm chart.
  8. API і worker розгортаються як окремі workloads.
  9. Після deployment перевірені health, login, Redis і контрольний job.
  10. Відома команда rollback і відповідальна особа.

14. Короткий runbook інциденту

API не відповідає

Перевірити pod/process, PostgreSQL connection, останню міграцію, config validation і application logs.

Дані не оновлюються

Перевірити worker, Redis, failed jobs, зовнішній API, credentials, `StudentSyncStatus`, stuck `RUNNING` і cron reconciliation.

Помилки лише одного студента

Перевірити externalId, статус студента, department/organization, останню помилку кожного sync type. Не виконувати wipe без резервного плану.

Платіж завис

Знайти `paymentRef`, `sid`, локальний status і `PaymentTranState`; звірити test/prod terminal та callback. Не змінювати фінальний статус SQL-командою без погодженої процедури.

Після релізу зросли помилки

Зупинити подальший rollout, порівняти API і worker versions, перевірити міграції, queue payload compatibility та виконати rollback.
