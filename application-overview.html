Що насправді знаходиться всередині u.Освіта

Розкладаю проєкт по частинах: що бачить студент, що робить worker, де лежать дані та які місця поки не можна називати завершеними.

Backend + Worker + Admin SPA Node.js / React / PostgreSQL Оновлено: 05.09.2026

1. Загальна інформація

u.Освіта — серверна освітня платформа для мобільного застосунку студента та внутрішньої адміністративної панелі. Вона об’єднує облікові записи користувачів, структуру університету, навчальні дані, фінансову інформацію та фонову синхронізацію із зовнішньою інформаційною системою закладу освіти.

Основна ідея: не звертатися до системи університету під час кожної дії студента, а періодично отримувати дані, перевіряти їх і зберігати локальну актуальну копію. Це прискорює мобільний API та дозволяє продовжувати читання вже синхронізованих даних під час короткочасної недоступності зовнішнього сервісу.

ПродуктМобільний API для студентів і web-панель для операторів.
Предметна областьОсвіта, розклад, оцінки, навчальний план, оплата та новини.
ДжерелаPostgreSQL, API університету, банківський процесинг, OTP/SMS/email.
Фонові процесиBullMQ worker із Redis, повторні спроби та контроль станів.

Схема містить 28 моделей і 20 enum. Центральна зв’язка — `User → UserStudent → Department → Organization`. Один користувач може мати кілька студентських профілів. Синхронізація контролюється окремо для студента або організації та конкретного типу даних.

6. Основні процеси

Реєстрація та верифікація

Телефон → OTP → реєстрація User → JWT
       → вибір університету → /studentinfo
       → створення UserStudent → запуск синхронізацій

Періодичне оновлення

Cron → BullMQ → Worker → API університету
     → нормалізація → транзакції Prisma
     → оновлення SyncStatus → дані доступні застосунку

Оплата

PaymentTemplate → StudentPayment → банківська сесія
     → hosted payment або token purchase → 3DS
     → callback/webhook → PaymentTranState → фінальний статус

8. Зовнішні інтеграції

  • Система університету: профіль, баланс, розклад, оцінки, календар, платежі, знижки та RSS.
  • OTP і SMS: підтвердження телефону та відновлення доступу.
  • Email: підтвердження адреси й сервісні повідомлення.
  • TASLink: payment link, токенізація, покупка, 3-D Secure та статус транзакції.
  • Kafka/Logstash: необов’язкова централізована доставка логів.

Поточна конфігурація університетського API глобальна. Для моделі «один університет — одна екосистема» потрібні окремі credentials, endpoint, branding, feature flags і графік синхронізації для кожного `organizationId`.

9. Безпека

Застосунок використовує JWT, Passport, password hashing, Joi validation, Helmet, XSS-фільтрацію, rate limiting, CORS і централізований error handler.

Основні ризики, які потребують закриття

  • Нерівномірне застосування authorization до адміністративних endpoints.
  • Глобальна роль ADMIN без обмеження університетом.
  • Вимкнена перевірка TLS-сертифіката MAUP.
  • Відсутність повного журналу адміністративних дій.
  • Необхідність обмежити CORS конкретними origin.
  • Фінансові та персональні дані потребують маскування в логах.
  • Відомі npm vulnerabilities мають бути проаналізовані без автоматичного force-upgrade.

10. Розгортання та експлуатація

API та worker масштабуються окремо. PostgreSQL є основним сховищем, Redis — інфраструктурою черг. Для Kubernetes у репозиторії є Helm chart. Dockerfile збирає backend і React SPA.

11. Поточні обмеження

  • Архітектура ще не забезпечує повну tenant-ізоляцію кількох університетів.
  • Немає моделей branding та налаштувань університету.
  • Немає окремого UI для платіжних транзакцій і карткових токенів.
  • Історія синхронізацій моделюється недостатньо: переважно зберігається поточний стан.
  • Стара EJS-адмінка співіснує з React SPA.
  • Маршрути `/admin`, `/admin/api` та `/api/admin` налаштовані неузгоджено.
  • Між Prisma-схемою та міграціями було виявлено розбіжність enum `SUSPENDED`.
  • Штатний test script посилається на відсутню команду `db:push`.
  • Назви деяких полів містять історичні помилки: `semestr`, `discaunt`, `edutaion`, `autidotirum`.

12. Рекомендований розвиток

  1. Закрити адміністративні endpoints єдиною authentication та permission policy.
  2. Додати tenant-моделі, ролі університету та автоматичний organization scope.
  3. Додати branding, feature flags і конфігурацію інтеграцій на університет.
  4. Виправити міграції та перевіряти чисте розгортання БД у CI.
  5. Додати історію запусків, correlation ID та audit log.
  6. Стандартизувати Provider API через затверджений OpenAPI і runtime validation.
  7. Додати платіжний operational dashboard.
  8. Прибрати старі EJS-сторінки після перенесення функцій.
  9. Уніфікувати маршрути frontend/backend/ingress.
  10. Додати contract, security, isolation, migration і end-to-end tests.
